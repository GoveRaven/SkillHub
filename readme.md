# ТЗ

## 1. Общая постановка задачи

Необходимо разработать fullstack-проект платформы онлайн-курсов, состоящий из:

* публичной витрины;
* CMS;
* корзины и оплаты;
* личного кабинета;
* страницы управления заказами;
* мониторинга ошибок;
* E2E-тестов;
* CI/CD;
* Docker-окружения.

Проект должен быть реализован как монорепозиторий

---

# 2. Функциональные требования

## 2.1. Публичная часть сайта

Сайт должен содержать:

### Главную страницу

На главной странице должны быть:

* hero-блок;
* список популярных продуктов/курсов;
* преимущества платформы;
* блок с FAQ;
* ссылки на контентные страницы.

### Каталог

Каталог должен позволять:

* просматривать список курсов;
* фильтровать по категории;
* переходить на карточку курса;
* работать с пагинацией или infinity scroll.

### Карточка курса

Карточка должна содержать:

* название;
* описание;
* цену;
* обложку;
* категорию;
* преподавателя/автора;
* блок FAQ или описание преимуществ;
* кнопку покупки.

### Контентные страницы

Нужно реализовать:

* статьи/блог;
* SEO-страницы;
* лендинги, управляемые из Strapi.

---

## 2.2. Оформление заказа

Пользователь должен иметь возможность:

* перейти к корзине;
* ввести необходимые данные;
* инициировать оплату;
* перейти в платёжный сценарий ЮKassa;
* вернуться на сайт после оплаты;
* увидеть результат платежа.

---

## 2.3. Платёжная интеграция

Необходимо реализовать интеграцию с **ЮKassa**:

### Обязательные сценарии

* создание платежа;
* редирект в платёжную форму;
* возврат пользователя на сайт;
* обработка webhook;
* обновление статуса заказа;
* обработка успешной оплаты;
* обработка отменённой/неуспешной оплаты.

### Требования к реализации

* использовать тестовый режим;
* не хранить чувствительные данные платежей на клиенте;
* платёж должен инициироваться на серверной стороне;
* обработка webhook должна быть идемпотентной;
* заказ должен иметь понятный жизненный цикл статусов.

### Предлагаемые статусы заказа

* `created`
* `pending_payment`
* `paid`
* `payment_cancelled`
* `payment_failed`

---

## 2.4. Личный кабинет

Личный кабинет должен быть вынесен в отдельный микрофронт и содержать:

### Страницы

* профиль пользователя;
* список заказов;
* страница деталей заказа;
* список приобретённых продуктов/курсов.

### Возможности

* просмотр статуса заказа;
* просмотр даты покупки;
* просмотр состава заказа;
* повторная попытка оплаты для неоплаченного заказа, если такой сценарий будет поддержан.

---

# 3. Нефункциональные требования

## 3.1. Архитектура

Проект должен быть организован как монорепозиторий. Основные приложения (Работа со Strapi, основной фронтенд и микрофронт) должны быть разделены по слоям. Общее (ui, типы, любые конфигурации и контраты) должно быть вынесено в отдельные пакеты/отделено для переиспользования

---

## 3.2. Микрофронт

Нужно реализовать **один** микрофронт для личного кабинета и управление заказами:
* Vite-приложение собирается как отдельный bundle;
* микрофронт встраивается в shell как отдельная точка входа;
* взаимодействие между shell и микрофронтом идёт через:
  * backend API;
  * общие контракты;
  * публичный интерфейс интеграции;
  * при необходимости custom events.

### Архитектурное правило

Основной shell и микрофронт не должны импортировать внутренний код друг друга напрямую.

---

## 3.3. State management

Использовать только:

* **TanStack Query**

### Область применения

Через TanStack Query должны работать:

* получение списка курсов;
* получение карточки продукта;
* получение данных профиля;
* получение списка заказов;
* получение деталей заказа;
* mutations для корзины и действий в кабинете.

### Допустимо

* локальный UI state хранить в state компонента;
* фильтры и навигационный state при необходимости хранить в URL.

---

## 3.4. Мониторинг

Нужно подключить **Sentry**.

### Что должно отслеживаться

* ошибки frontend в Next.js;
* ошибки route handlers/backend-части shell;
* ошибки микрофронта;
* ошибки в платёжных сценариях;
* ошибки при обработке webhook.

### Минимум

* базовая интеграция;
* разделение ошибок по приложениям;
* release name/tag (опционально).

# 6. API и серверная логика

## 6.1. Обязательные серверные сценарии

Нужно реализовать серверные обработчики для:

* получения данных корзины;
* создания заказа;
* создания платежа в ЮKassa;
* обработки возврата после оплаты;
* обработки webhook;
* получения заказов пользователя;
* получения деталей заказа.

## 6.2. Бизнес-логика заказа

При покупке:

1. создаётся заказ;
2. заказ получает статус `pending_payment`;
3. создаётся платёж в ЮKassa;
4. пользователь переводится в платёжный сценарий;
5. после webhook статус обновляется;
6. после успешной оплаты заказ становится доступен в личном кабинете.

# 7. Тестирование

## Инструмент

* **Playwright**

## Область тестирования

Нужно сделать только E2E.

## Обязательные сценарии

### Сценарий 1. Успешная покупка

* пользователь открывает каталог;
* открывает карточку товара;
* переходит в корзину;
* проходит тестовый сценарий оплаты;
* возвращается на сайт;
* видит успешный статус заказа;
* видит заказ в личном кабинете.

### Сценарий 2. Неуспешная/отменённая оплата

* пользователь доходит до корзины;
* оплата не завершается успешно;
* статус заказа отображается корректно.

### Дополнение

В CI допустимо использовать стаб/мок вокруг платёжного сценария, чтобы не зависеть от реального внешнего сервиса на каждом прогоне.

# 13. Критерии готовности

Проект считается завершённым, если:

* работает публичная витрина;
* контент управляется через Strapi;
* можно создать заказ и пройти тестовый сценарий оплаты;
* webhook обновляет статус заказа;
* заказ отображается в личном кабинете;
* кабинет вынесен в отдельный Vite-микрофронт;
* ошибки собираются в Sentry;
* есть Playwright E2E;
* настроены линтеры и git hooks;
* проект запускается через Docker;
* CI pipeline проходит успешно.
